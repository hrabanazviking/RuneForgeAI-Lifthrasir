**Project:** Lífþrasir — The Self-Evolving Linux System
**Slice:** LIF-0404 (Phase P4) — user approval UX and signed/unique plan references.
**Status honesty:** Contract/test-level implementation in
`src/lifthrasir/approval.py`, proven by `tests/test_approval.py` at

contract scope). No interactive UI, no live broker, no host change
is implemented or claimed. Human review: **pending**.

## Contracts implemented

1. **Plan digest.** A v0.1 plan record (LIF-0004) is digested over
   its canonical JSON (sorted keys, compact separators):
   `sha256:<64 hex>`. Any edit to the plan — title, step, target —
   changes the digest, so an approval can never silently transfer
   to an edited plan.
2. **Signed, unique reference.** `mint_plan_reference` issues a
   `PlanReference`: plan id, digest, a fresh nonce (16-64 hex,
   caller-supplied in tests, `secrets`-generated by default), the
   exact resource scope (sorted `type:name` over all plan steps),
   issue/expiry times, and an HMAC-SHA256 signature over all of
   those fields. Reference expiry is the earlier of the TTL
   (default 900 s) and the plan's own `expires_at`. A ledger
   refuses to register the same nonce or reference twice:
   references are unique and never re-issued.
3. **Approval prompt (UX).** `render_approval_prompt` renders a
   deterministic plain-text prompt with separate sections —
   WHAT IS PROPOSED, EXACT SCOPE, PRECONDITIONS, ROLLBACK,
   VERIFICATION, REFERENCE AND EXPIRY — plus a human-comparable
   short check code (first 12 digest hex digits, grouped). Per
   ADR-0002 Decision D3, the prompt and the approval record carry
   the plan hash, resource, decision and expiry only: never key
   material, never step arguments (which may hold sensitive
   values), never secrets.
4. **Decisions.** `ApprovalLedger.decide` records one terminal
   decision (`approved`/`rejected`, named approver, timestamp).
   `consume_for_execution` consumes an approval exactly once, for
   one resource inside the approved scope, before expiry. Replay,
   substitution (digest mismatch), expiry, wrong resource, and a
   second decision all raise named errors and change nothing.

## Consent rules (from docs/RISK-MATRIX.md, LIF-0003)

- The plan's declared `consent_mode` must be at or above the floor
  for its `risk_level` (L0 `none` ... L4 `per-action`, L5
  `human-only`); below-floor plans are refused at mint time.
- `consent_mode: never` is refused outright: no consent authorizes
  an agent to execute the prohibited class (section 0 invariants).
- L5 `human-only` plans may be referenced and prompted (an agent
  may prepare them for human review); execution in a maintenance
  environment is a human act outside this contract (not claimed here).

## Coordination gaps (flagged, not hidden)

- **LIF-0401/0402/0403 were building in parallel** when this slice
  was built. This slice depends only on banked contracts (v0.1 plan
  schema, risk matrix, ADR-0002 D3) and defines its own reference
  shape; when the typed action catalog (0401) and policy engine
  (0402) bank, `action_verb` validation and policy-decision input
  wiring are the follow-up integration, recorded here rather than
  assumed.
- **Durable storage is LIF-0405.** The ledger here is in-memory;
  crash-safe persistence and the undo manifest belong to that
  slice. Nothing in this slice claims durability.
- **Signing is fixture-scale.** HMAC with caller-supplied bytes is
  a testable stand-in for the protected key mechanism of
  research/22 (sign only after human/policy approval). No real
  key — and no DCO tag — is ever used or produced by agents.
